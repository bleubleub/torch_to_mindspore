为什么这样做

目标不是替换整个 migrate 流程，而是补齐当前最弱的 generic PyTorch 路由。

保留专项路线

HF 路由不动

hf-transformers 和 hf-diffusers 继续走已有专项规则， 避免把通用迁移逻辑误套到成熟流程上。

增强通用场景

generic 路由结构化

generic PyTorch 仓库先扫描和映射，再让 LLM 改写，减少只靠提示词迁移带来的随机性。

可复查

改完必须复扫

迁移完成不以 LLM 自述为准，而以二次扫描的残留 API、未映射项和低置信度项作为验收依据。

执行链路

这条链路只在 generic-pytorch-repo 被选中时启用。

01

路由判断

migrate-agent 先分析仓库类型。若不是 HF transformers 或 diffusers， 并且是普通 PyTorch 项目，则进入 generic PyTorch route。

migrate-agent route-selector
02

迁移前置检查

/migrate 进入 generic route 后先显示 readiness。若检测到 pyright-langserver 或 basedpyright-langserver， 启用 LSP 增强识别；若缺失，则提示安装方式并继续使用静态扫描。

readiness optional pyright fallback
03

API 扫描和映射

调用 torch_migration_scan，Go 原生扫描 Python 文件， 识别 PyTorch API、常见 alias 和 Tensor 方法候选；LSP 可用时对低置信度项做类型确认， 再匹配内置 JSON 映射。

torch.* nn / F alias hover / definition mapping JSON
04

文件级上下文

对需要修改的文件调用 torch_migration_file_context， 返回该文件 API 列表、映射建议、备注、风险提示和源码片段。

run_id file context risk hints
05

LLM 直接改写

不做机械替换。agent 使用现有 read/edit/write 工具， 按上下文理解源码并进行 MindSpore 化改写。

read edit write
06

复扫与报告

修改后再次扫描，输出残留 Torch API、未映射 API、低置信度项、人工处理项和最终迁移摘要。

rescan residual report acceptance

Readiness 与 LSP 策略

Pyright 是可选增强依赖，不随 ms-cli 安装强制下载。

内置 Pyright-only LSP

第一版不做通用 plugin LSP。ms-cli 内置 Python/Pyright LSP 调用能力， 只在迁移场景需要类型确认时启动。没有 Pyright 时不阻塞迁移，静态扫描继续工作。 

Migration readiness:
  route: generic-pytorch-repo
  pyright-langserver: missing
  lsp-enhanced detection: disabled
  fallback scanner: enabled

To enable better Tensor/API type detection:
  npm install -g pyright
  pyright-langserver --version

新增 Tool 形态

Tool 是只读分析能力，默认权限按 read/glob 类工具处理。

torch_migration_scan

repo-level 
{
  "path": ".",
  "include_tests": true,
  "limit": 100
}
  • 递归扫描 Python 文件。
  • 识别 torch API、import alias 和 Tensor 方法候选。
  • Pyright LSP 可用时，对低置信度候选做 hover/definition 类型确认。
  • 匹配内置 MindSpore 映射 JSON。
  • 返回 run_id、覆盖率、按文件聚合列表和临时产物路径。

torch_migration_file_context

file-level 
{
  "run_id": "mscli-migrate-20260514-xxx",
  "file": "models/net.py"
}
  • 读取扫描产物里的文件级 API 记录。
  • 返回可替换接口、其他替代方案、备注和风险提示。
  • 补充源码片段，帮助 LLM 按上下文改写。
  • 避免一次把全仓库塞给模型。

实现边界

第一版重点是把迁移流程从“自由发挥”变成“结构化辅助改写”。

第一版包含

  • Go 原生扫描器：不依赖 Python、pandas 或 libcst。
  • 内置 Pyright-only LSP：Pyright 存在时增强类型确认，缺失时降级静态扫描。
  • 迁移 readiness 提示：在 /migrate 前置检查里显示 Pyright 状态。
  • 内置 JSON 映射：由现有 Excel 映射表生成。
  • 临时产物：默认写入系统临时目录，不污染用户项目。
  • skill 文档更新：generic route 强制 scan、context、edit、rescan。

第一版不包含

  • 不强制安装 Pyright，用户未安装时只提示并继续迁移。
  • 不做通用 LSP plugin 系统，先只服务 Python/PyTorch 迁移。
  • 不做机械自动替换，源码改写由现有 agent 完成。
  • 不新增专用 LLM SDK 流程，复用 ms-cli provider 和 agent loop。
  • 不替换 HF 专项流程，只增强 generic PyTorch route。

验收标准

迁移结果由扫描产物和残留报告支撑，而不是仅凭模型回答。

Tool Tests

扫描能力正确

覆盖 import alias、API 映射命中、未映射、Tensor 方法低置信度和忽略 .git、__pycache__、虚拟环境目录；同时覆盖 Pyright 存在/缺失两种 readiness 分支。

Skill Tests

流程要求明确

generic route 文档必须包含 scan、file context、agent edit、rescan； HF transformers/diffusers 文档不能被 generic 流程覆盖。

Integration

端到端可跑

用小型 PyTorch repo 验证 /migrate 会先扫描、再改写、最后复扫并报告残留风险。

最终形态

/migrate 仍然是统一入口；migrate-agent 仍然负责路由。 只有当 route 选择为 generic-pytorch-repo 时，才启用 torch_migration_scan 和 torch_migration_file_context。 如果本机存在 pyright-langserver，扫描阶段会启用 LSP 增强识别；如果缺失， /migrate 会展示 readiness 提示并降级到静态扫描。 这样既保留已有专项迁移能力，又把普通 PyTorch 仓库迁移从“提示词驱动”升级为 “readiness 检查 + 扫描证据 + 类型确认 + 映射约束 + LLM 改写 + 复扫验收”的稳定链路。
